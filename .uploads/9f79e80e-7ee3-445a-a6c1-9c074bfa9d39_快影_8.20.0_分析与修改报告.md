## 二、防护体系分析

### 2.1 签名与完整性防护（`com.kwai.videoeditor.support.security`）

该包是快影自研的反篡改模块，核心类为 `ApkGuardHelper`。其防护逻辑分为三层：

**第一层：远程黑名单签名校验**

`ApkGuardHelper->checkRemoteBlockSignature()V`

- 由远程配置开关 `enable_black_signature_check` 控制
- 从 `black_signature_list` 拉取黑名单签名数组
- 通过 `parseSignatureFromApk()` 读取当前 APK 签名，与黑名单比对
- 命中后走 `applyIllegalApkStrategy()` 执行处置

关键辅助方法 `parseSignatureFromApk()V` 通过 `getPackageCodePath()` 与 `getBaseApkPathFromRuntime()`（后者用 `Runtime.exec("pm path ...")` 获取真实 APK 路径）双重定位安装包，再解析其证书。

**第二层：设备黑名单校验**

`ApkGuardHelper->checkRemoteBlockDeviceId()V`

- 由 `enable_black_device_id_check` 控制
- 黑名单来源 `black_device_id_list`
- 用于封禁已标记的调试设备

**第三层：处置策略（`IllegalApkStrategy` 枚举）**

| 枚举值 | 行为 |
|---|---|
| `DO_NOTHING` | 不处理 |
| `KILL` | 直接杀进程 |
| `DIALOG` | 弹窗提示 |
| `NO_ALLOW_CANCEL_DIALOG` | 不可取消弹窗 |
| `DIALOG_UPGRADE` | 强制升级弹窗 |

策略数值来自远程开关 `guard_illegal_apk_strategy`，由 `getIllegalApkStrategy()` 读取并经 `IllegalApkStrategy$Companion.fromNumber()` 转换。

实际终止手段有两套冗余实现：

- `doKill()` → `Process.killProcess(myPid())` + `System.exit()`
- `killByReflect()` → 通过 `JavaCalls.callStaticMethod()` 反射调用 `android.os.Process.killProcess` 与 `java.lang.System.exit`（规避静态特征扫描）

### 2.2 会员体系（`com.kwai.videoeditor.vip`）

会员状态的**唯一数据来源**是 `VipStatus` 对象，字段均为 `final`，由服务端下发后构建：

```
VipStatus 关键字段：
  isVip:Z                  ← 会员总开关
  isSubscription:Z         订阅会员
  purchasedVipProduct:Z    已购会员产品（含 SwitchUtil 实验开关）
  vipInfoValid:Z           会员信息有效
  vipType:Integer          会员类型
  kuaiBeanAmount:Integer   快币余额
  vipValidTime:J           有效期
```

代码中的会员判断高度集中，收敛在两个方法：

- `VipStatus->isVip()Z` —— 最底层 getter，被 **50+ 处** 直接调用（编辑页、字幕、AI 拆分、音乐 MV、质量优化、虚拟人生成等）
- `VipWrapper->i()Z` —— 上层封装，本质仍是 `b()` 取 `VipStatus` 后调用 `isVip()`

这一结构意味着：**改一处 `isVip()` 即可覆盖绝大多数会员卡点**，无需逐个修改业务代码。

### 2.3 付费模板体系

模板付费判断分散在两条独立链路：

**链路 A：模板详情页「使用」按钮** —— `ChargeableUseButtonPresenter`

- `z6()Z`：判断是否为潜在付费模板（`TemplateBeanExtKt.isPotentialVip`），若成立则发起 `isPotentialVipRequest` 网络请求，并 **返回 true**
- `R6(Z)` / `y6()Z`：模板「可免费使用」状态（字段 `q0`）的 setter/getter
- `refreshTemplateFreeStatus$1`：依据服务端返回的 `payTemplateLockStatus` 决定按钮状态

**链路 B：付费委托器** —— `ChargeableTemplatePayDelegateV2`

`initFreeStatus$1$1` 同样读取 `payTemplateLockStatus`，为 `false` 且模板 `isChargeable()` 时把状态置为 `PayStatus.Free`。

模板锁状态字段：`TemplatePayModel->payTemplateLockStatus:Boolean`

## 三、修改方案

### 3.1 设计原则

1. **最小改动**：只改判定函数入口，不动业务逻辑，降低崩溃与功能异常风险
2. **等长/小范围插入**：所有改动通过 Smali 方法体重写实现，不改变方法签名与寄存器约定
3. **兜底优先**：先废防护，再改功能，避免改完功能被杀

### 3.2 改动清单（共 3 个类 / 7 处）

## 五、风险与已知限制

### 5.1 服务端校验不可绕过

本次修改全部在**客户端判定层**。以下场景依然可能失败：

- 导出时服务端校验 VIP 权益（服务端返回的权益位为 false）
- VIP 专属素材/模板/音色在**下载阶段**被服务端拒绝
- 云端渲染、AI 生成类功能（服务端计费）

### 5.2 加固层风险

- 类中存在大量 `PatchProxy` 桩，说明有方法级加固。若加固在运行时做了 **方法体校验或 CRC 自检**，篡改可能触发异常
- `Robust` 热修复框架会缓存补丁，极端情况下可能覆盖已修改的方法
- 本方案验证了 **静态可达路径**，未做运行态验证

### 5.3 功能正确性限制

- `y6()` 强制为 true 后，模板状态 UI 可能显示为免费但下载仍失败（服务端侧）
- `z6()` 返回 false 会跳过潜在付费探测，部分营销类模板的引导逻辑将被跳过
- 部分强依赖 `VipStatus` 真实字段值（如 `vipValidTime`、`kuaiBeanAmount`）的功能仍按真实值运作

### 5.4 签名变更影响

重签名后与原包签名不一致，会导致：
- 无法覆盖安装（需先卸载原版，草稿数据会丢失）
- 微信/QQ 等 OpenSDK 第三方登录、分享可能失效（这些 SDK 自带签名校验）
- 部分厂商推送、支付 SDK 可能拒绝初始化
